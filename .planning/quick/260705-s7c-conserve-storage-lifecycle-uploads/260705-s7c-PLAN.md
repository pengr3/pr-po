# Quick Task 260705-s7c: Conserve Storage for Lifecycle-Gate Uploads

## Origin

Follow-on to **quick 260704-luf**, which re-added Firebase Storage file upload on the
four lifecycle gate documents (Inspection Report, NTP, Completion Report, COC) for
both projects and services. Now that bytes actually land in Storage, the user asked to
conserve space on two fronts:

> 1. "limit file size … the files to be uploaded"
> 2. "what happens to files for already completed project — can we somehow archive
>    this that … uses little to no space … and once recovered from archive only from
>    then on its files will resurface"

## Reality check (drives the design)

- **Scale is tiny.** 4 report PDFs per project (~0.5–3 MB each), deterministic paths
  (`projects/{id}/<docKey>.<ext>` — one object per doc type, re-upload overwrites). Free
  tier is **5 GB stored**; growth is linear and slow. This is hygiene + a worst-case
  cap, not an urgent cost problem.
- **A client-only SPA cannot cheaply cold-store bytes.** The browser Firebase SDK can
  upload/download/delete objects but **cannot** change an object's storage class
  (Standard→Archive) or set bucket lifecycle rules. So:
  - The *"hide files until recovered"* half is pure in-app work (Firestore flag + render).
  - The *"shrink the GB bill"* half is a **one-time operator step** (a GCS bucket
    lifecycle rule) — the actual cost lever. The two are decoupled on purpose.
- **No deletion anywhere.** Recover must always work in one click, so we never delete
  bytes; the cold-rule only *transitions class* (Archive objects stay instantly readable
  via the same download URL, for a tiny retrieval fee).

## Decisions (confirmed with user)

- **Upload cap 10 MB → 5 MB** + surface the limit/size in the UI. Ext allowlist unchanged.
- **Archive = app-level hide/recover + bucket cold-rule** (not byte-moving, not deletion).
- **Archive trigger = after DLP/warranty expires** (keeps files hot while a defect claim
  is still possible); for Completed projects with no DLP, a grace window after completion.
- **Parity**: implement in both `project-detail.js` and `service-detail.js`.

## Tasks

### T1 — Lower ingestion cap to 5 MB + surface it (both detail views + rules)

1. `project-detail.js` and `service-detail.js`: `LC_UPLOAD_MAX_BYTES` → `5 * 1024 * 1024`;
   change the two reject-toast strings "10 MB" → "5 MB".
2. `storage.rules`: `size < 10 * 1024 * 1024` → `< 5 * 1024 * 1024` in **both** the
   `projects/{projectId}/**` and `services/{serviceId}/**` blocks (keep the
   `request.resource == null` delete guard). Reads are not size-gated, so any existing
   >5 MB object stays readable; only new writes >5 MB are blocked.
3. `buildAttachZone` upload panel (the file-input row, `project-detail.js:2547-2549` +
   service twin): add a caption under the input — `Max 5 MB · PDF, DOC, DOCX, PPTX, XLSX,
   PNG, JPG` — and an `onchange` on the file input that shows the picked file's name +
   size (KB/MB) so users see it before clicking Upload. Keep the existing `accept` attr.

### T2 — App-level Archive / Recover (project side)

Derived hide (no write) + one explicit Recover write. Files stay in Storage; this is the
UX half — "files gone from the view until recovered."

1. Add constant `LC_FILES_ARCHIVE_GRACE_DAYS = 365` (tunable) and helper
   `isLcFilesArchived(project)` near `getDlpState` (~`project-detail.js:950`):
   ```js
   function isLcFilesArchived(p) {
     if (!p || p.files_recovered) return false;            // explicit un-archive override
     if (p.project_status !== 'Completed') return false;
     const dlp = getDlpState(p);                            // call exactly as renderDlpFinanceBar does
     if (dlp === 'in-dlp') return false;                    // still under warranty → keep hot
     if (dlp === 'expired' || dlp === 'released') return true;
     // dlp === 'active' → no DLP configured on this project: grace window after completion
     const doneMs = p.project_completed_at ? new Date(p.project_completed_at).getTime() : 0;
     return !!doneMs && (Date.now() - doneMs) > LC_FILES_ARCHIVE_GRACE_DAYS * 86400000;
   }
   ```
2. `buildAttachZone` `hasDoc` branch (2521-2535): when `isLcFilesArchived(project)`,
   replace the clickable `<a>` (line 2530) + Remove button with a muted archived state —
   `📦` icon, greyed doc name, sub-label "Archived to conserve storage" — and no working
   link. Render a **single project-level** `♻ Recover files` control (one flag recovers
   all four gate docs at once); gate it to assigned/admin users (same capability check the
   view already uses for lifecycle actions).
3. Also mute the Completion "Completed"-cell doc labels that link/echo
   `completion_report_*` / `certificate_of_completion_*` (`project-detail.js:2708-2717`)
   when archived — show a `📦 archived` marker instead of a live reference.
4. Add `window.lcRecoverFiles(projectId)`:
   ```js
   await updateDoc(doc(db,'projects',projectId), {
     files_recovered: true,
     files_recovered_at: serverTimestamp(),
     files_recovered_by: currentUser?.uid || currentUser?.email || null,
     updated_at: serverTimestamp(),
   });
   await addProjectAuditEntry(projectId, 'LC_FILES_RECOVERED', ...);   // + optional _addActivityEntry system line
   ```
   **Register in `init()`, delete in `destroy()`** (window-fn register↔teardown symmetry —
   hard rule in this repo). Optional companion `window.lcArchiveFilesNow(projectId)` that
   sets `files_recovered: false` to re-hide.

### T3 — Firestore rules field-mask (projects)

Add `files_recovered`, `files_recovered_at`, `files_recovered_by` to the **projects**
assigned-user `hasOnly()` field-mask (`firestore.rules:226-248`), mirroring how
`*_storage_path` was added in 260704-luf — otherwise an assigned non-admin's Recover write

### T4 — Service-detail parity

Mirror T1 (cap + caption) and T2 (archive/recover) into `service-detail.js`: service

`window.lcServiceRecoverFiles` writes `files_recovered*` on `services/{id}` (no field-mask,
so no rules change); register↔teardown symmetric. storage.rules services cap already
handled in T1.

### T5 — Purge Storage objects on project/service delete (the leak)

Deleting a project/service doc currently leaves its `projects/{id}/*` (or `services/{id}/*`)
Storage objects orphaned — an unbounded drip that undermines the whole task. Three delete
sites, all admin-only, same shape (guard → confirm → `deleteDoc` → toast):
`projects.js:1456-1478` (`deleteProject`), `project-detail.js:1890-1911` (`confirmDelete`),
`services.js:1511-1540` (`deleteService`). (No service-detail delete path exists.)

1. `app/firebase.js`: add `listAll` to the firebase-storage import (alongside the existing
   `ref/uploadBytes/getDownloadURL/deleteObject`, ~lines 47-53) and export one best-effort
   helper (also expose on `window.firebaseStorage`):
   ```js
   export async function purgeStoragePrefix(prefix) {
     try {
       const res = await listAll(ref(storage, prefix));
       await Promise.all(res.items.map(it => deleteObject(it).catch(() => {})));
       return res.items.length;
     } catch (e) { console.error('[Storage] purge failed:', prefix, e); return 0; }
   }
   ```
   `listAll` is the right tool: the list-view handlers only receive `(id, name)` — not the
   doc's `_storage_path` fields — so a prefix sweep also catches any partial-failure
   orphans. (`allow read` on `projects/{id}/{allPaths=**}` covers the list operation.)
2. In each of the 3 sites: **after** the successful `await deleteDoc(...)` (doc first, so we
   never purge a still-live entity), best-effort `await purgeStoragePrefix('projects/' + id)`
   / `'services/' + id`, wrapped so a Storage failure never throws to the user (the doc is
   already gone; just log). Add the `purgeStoragePrefix` import to `projects.js` /
   `services.js` (neither imports Storage yet); `project-detail.js` already imports the
   Storage surface.
3. **Fallback** if UAT shows `listAll` denied by list-permission: enumerate the 4
   `LC_DOC_KEYS` and `deleteObject(ref(storage, p[dk+'_storage_path']))` for each present
   field (`project-detail` has `currentProject`; the list views would need a `getDoc` first).

## Operator punch list (not code — the real GB-cost lever + deploy)

1. **Redeploy rules** to dev **and** prod (per `firebase-dev-prod-deploy`: CLI active
   project is PROD, so also pass `--project dev`):
   `firebase deploy --only storage,firestore:rules` (dev, then prod).
2. **Set the GCS bucket lifecycle rule** on **both** default buckets
   (`clmc-procurement-dev.firebasestorage.app`, `clmc-procurement.firebasestorage.app`).
   Transition-only, **no delete action** (so Recover always works):
   ```json
   {"rule":[
     {"action":{"type":"SetStorageClass","storageClass":"COLDLINE"},"condition":{"age":90}},
     {"action":{"type":"SetStorageClass","storageClass":"ARCHIVE"},"condition":{"age":365}}
   ]}
   ```
   `gcloud storage buckets update gs://<bucket> --lifecycle-file=lifecycle.json`
   Verify: `gcloud storage buckets describe gs://<bucket> --format="default(lifecycle)"`.
   Caveat: Archive class has a 365-day minimum-storage-duration (early delete/overwrite of
   a cold object incurs a prorated fee — negligible here; completed-project files aren't
   re-uploaded).
3. **One-time orphan backfill (optional, low priority).** Sweeps objects left by
   projects/services hard-deleted *before* T5 shipped. The client can't list the bucket
   root (rules expose only `projects/**` / `services/**`), so do it operator-side in Cloud
   Shell: `gsutil ls gs://<bucket>/projects/` and `.../services/` → diff the id-prefixes
   against the live `projects`/`services` collections → `gsutil -m rm -r
   gs://<bucket>/<collection>/<orphanId>`. Near-zero expected (feature shipped today).
4. **Browser UAT** (see Verification).

## Verification

- **Cap:** upload a 6 MB file → rejected with "5 MB"; a 4 MB PDF → succeeds. Caption +
  live size render in the upload panel. Rules reject a >5 MB write server-side.
- **Archive (derived):** a Completed project **past DLP** (or `getDlpState === expired/
  released`, or no-DLP + >365 d since completion) shows gate docs as `📦 Archived` + a
  Recover control; links are gone. A Completed project **in-DLP** still shows working
  links. A non-completed / active project is unchanged.
- **Recover:** click Recover → links return, `files_recovered` persists across reload
  ("only from then on do they resurface"). An **assigned non-admin** can Recover
  (field-mask permits it); a >5 MB write is still denied.
- **Parity:** repeat the archive/recover + cap checks on a **service**.
- **Purge on delete (T5):** upload a file to a throwaway project, then delete it → confirm
  `projects/{id}/*` is gone from Storage (Firebase console) and no error surfaced. Repeat
  via the **detail-page** Delete and via a **service** delete. Deleting an entity with no
  files is a clean no-op.
- **Cold-rule:** `gcloud storage buckets describe` shows both transition rules on dev +
  prod. (Class transition itself is time-based and invisible to the app; recovery of a
  cold object still opens via the existing download URL.)

## Out of scope / follow-ups

- **Client-side byte-moving** to a cold prefix — not worth it at this scale; the bucket
  cold-rule delivers the GB savings with zero app complexity and no early-deletion fees.
- **Auto-deletion** of any files — never; would break Recover.
- **Image re-encoding / compression** on upload — PDFs dominate and can't be shrunk
  client-side cheaply; deferred.
- **Pre-existing orphans** from projects/services deleted before T5 — cleaned by the
  optional operator backfill (punch-list item 3), not code. All *new* deletes are covered
  by T5.
