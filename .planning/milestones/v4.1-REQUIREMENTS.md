# Requirements: Assignment Source-of-Truth & Read Enforcement

**Defined:** 2026-08-11 (retroactively, at milestone definition — see note below)
**Milestone:** v4.1 — Assignment Source-of-Truth & Read Enforcement
**Core Value:** Projects tab must work — it's the foundation where project name and code originate, and everything in the procurement system connects to it.

## Note on retroactive definition

This milestone was defined **after** its work was executed. Phase 113 was planned and run as an
urgent response to a live production defect, outside any milestone, and given the number 113 rather
than 106 to avoid colliding with the v4.2 branch's phases 106–112.

There is therefore no separate requirements-gathering artifact. The requirement set **is** the
locked decision set in `.planning/phases/113-assignment-source-of-truth-and-project-read-enforcement/113-CONTEXT.md`,
recorded as D-01 … D-17 and reproduced below in requirement form. Each is traced to the plan that
delivered it. This is why every phase artifact refers to "D-IDs" rather than "REQ-IDs".

## The problem this milestone solves

A `services_user` assigned to a project via the Personnel panel could not see it on `#/projects`,
nor file MRFs against it.

Root cause, confirmed by RED/GREEN emulator reproduction: `firestore.rules` permitted only
same-department admin→user writes on `users`, so `syncPersonnelToAssignments`' cross-department
`updateDoc` was `PERMISSION_DENIED` — and that failure was swallowed by a fire-and-forget
`.catch()`. The derived `assigned_project_codes` array silently stayed empty while the UI reported
the assignment as successful.

This was the **fourth** recurrence of the same bug class. Quick fixes 260627-kg0, 260706-mco and
260722-msg each patched a different read or UI layer without ever auditing the write layer. This
milestone eliminates the class rather than the instance: it removes the derived data entirely and
makes the container document's `personnel_user_ids` the single authoritative record.

## v4.1 Requirements (D-01 … D-17)

### Read model and enforcement

- [x] **D-01**: `firestore.rules` grants unrestricted `projects` reads to the see-all roles; scoped roles are enforced server-side. Server-side enforcement binds scoped roles only — a correctness and consistency fix, not a containment boundary against admins. *(113-10)*
- [x] **D-02**: Every scoped read standardises on `where('personnel_user_ids','array-contains',uid)`, removing the Firestore 30-value `in` ceiling that `where('service_code','in',codes)` silently carried, and guaranteeing by construction that every returned document satisfies the rule predicate. *(113-03 … 113-08)*
- [x] **D-03**: Audit-first, then convert everything found. A partial conversion is worse than none — once the rule tightens, an unscoped query is denied *in its entirety*, so a missed surface becomes a hard failure rather than a degraded one. *(113-09, `113-CONVERSION-AUDIT.md`)*
- [x] **D-04**: The 260615-nlj no-leak invariant carries over unchanged, with regression coverage. *(verified byte-identical in 113-06; automated symmetrically in `verify-crossdept-admin-scoping.js`)*
- [x] **D-15**: `projects` read is split into `allow get` / `allow list`, **both** scoped on `personnel_user_ids`, so a scoped role cannot reach an unassigned project by direct doc-ID link either. *(113-10)*
- [x] **D-16**: D-01's framing corrected — `services_admin` is *also* a scoped role for `projects`, and `operations_admin` for `services`. A plan written against the literal "only `*_user` roles" wording would have missed three MUST-CONVERT sites, exactly as the preliminary audit did. *(113-10, resolved as Option B)*

### Write model

- [x] **D-05**: The Assignments tab writes `personnel_user_ids` directly on project/service documents; `syncAssignmentToPersonnel` deleted. *(113-08)*
- [x] **D-06**: Supersedes the 260706-mco lock on `saveManageModal`. That lock existed to avoid the `all_projects:false` landmine while the arrays were still authoritative; once the arrays are not read, the landmine is gone. *(113-08, recorded explicitly in code)*
- [x] **D-07**: Full project↔service parity. The documented "intentional asymmetry" dissolves rather than being implemented — with one authoritative record there is nothing to sync in either direction. *(113-01, 113-10)*
- [x] **D-08**: Stop reading *and* writing the legacy arrays; do **not** delete the fields. They become frozen, inert rollback insurance. Field deletion is an irreversible write against production with no staging. *(113-03, 113-09)*
- [x] **D-09**: `all_projects` / `all_services` survive as role-independent see-all escape hatches — a *grant*, not assignment data. *(113-01, 113-10; status-gated per T-113-55)*
- [x] **D-10**: Display surfaces repoint to personnel-derived data — `user-management.js` assignment counts and `assignments.js` code display. *(113-08)*

### Failure-mode elimination

- [x] **D-11**: Retiring the syncs **is** the silent-failure fix, preferred over adding error plumbing to a doomed code path. Exactly one write per assignment remains, and it is awaited and toasted. *(113-08, 113-09)*
- [x] **D-12**: Standing constraint — no assignment-affecting write may be fire-and-forget. Any residual `.catch(err => console.error(...))` on an assignment path is a defect, not a style choice. *(113-09 sweep: zero assignment-affecting hits)*

### Scope corrections made during execution

- [x] **D-13**: The services side is converted in this phase too. Deleting `syncServicePersonnelToAssignments` stops `assigned_service_codes` being written, so a `services_user` assigned *after* this ships would never see their own new service — a services-side variant of the very defect being fixed. The phase boundary widened from `projects` alone to assignment read enforcement across `projects` **and** `services`. *(113-01, 113-04, 113-06)*
- [x] **D-17**: The `users.update` cross-department carve-out is dropped and its tests kept, inverted. Under D-05/D-08 every client path that made those writes is deleted, so the carve-out granted permissions nothing could exercise. The inverted tests are permanent regression coverage against the rules-layer-drifts-from-the-assignment-model bug class this investigation chain kept rediscovering. *(113-10; 9 tests, not the 8 RESEARCH.md claimed)*

### Explicitly deferred

- [ ] **D-14**: Residual subcollection exposure is **deferred, not closed**. `activity_entries`, `progress_updates`, `issues`, `audit_log`, `baselines` and `edit_history` all keep `allow read: if isActiveUser()` and none consult the parent's `personnel_user_ids`. After this milestone a scoped user cannot *discover* an unassigned project, but a known or guessed document ID still reads its journal and audit data. **Documented in `firestore.rules` itself** so the scoped parent rule cannot be mistaken for complete read scoping. Closing it is its own phase.

## Delivered beyond the original decision set

Work that was not in D-01 … D-17 but proved necessary during execution:

- **Counter-document CLMC code generation.** `generateProjectCode()` / `generateServiceCode()` range-scanned both collections for collision avoidance (CODE-01), making a cross-collection LIST read a prerequisite of creating anything — the reason `services_admin` could not be scoped. Replaced with an atomic `code_counters/{client}_{year}` transaction. This is what made D-16's Option B possible, and it also closed the simultaneous-create race the previous implementation documented and accepted. *(113-10, `cf0fa92`)*
- **Two read surfaces RESEARCH.md's table never enumerated** — `service-detail.js` and `service-plan.js`, both denying every scoped role. The first was found by browser UAT, the second by enumerating read sites from the code rather than from the research document. *(`e859d55`, `9f527da`)*
- **A fourth composite index**, `services × service_code × personnel_user_ids`, required by those conversions.
