<objective>
Close the two properties that only production can prove.

Everything else in this phase is a source assertion or a localhost observation. These two are not.
A CSP-blocked ingest request throws no catchable JavaScript error — the app behaves perfectly, the
console stays clean, and the dashboard shows zero events, which looks exactly like a healthy system
with no bugs. The only way to distinguish those two states is to fire a real event from the real
production origin and watch it arrive. And the degradation path — the app working normally when the
bundle is blocked — is meaningless as a code review; it has to be observed.

Purpose: turn "should work" into "was observed working", from the production origin.
Output: no code changes. Two human-verified gates and an evidence record.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Production browser → Sentry ingest through the live CSP | The one boundary no static analysis can validate; the policy either permits the request or silently drops it with no JavaScript-observable signal |
| Ad-blocker / extension layer → the page | An extension can block the bundle or the ingest request independently of CSP, producing an identical symptom from a different cause |
| Verifier's production session → real business data | This gate exercises a real write against production Firestore |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-28 | Repudiation | A silently CSP-blocked ingest presenting as "no errors occurred" | mitigate | The gate is a positive test: a specific event id produced in the browser must be found in the dashboard. Absence of console errors is explicitly not accepted as evidence |
| T-114-29 | Information Disclosure | A scrub regression reaching production and being unrecoverable | mitigate | The production event is inspected in the dashboard for supplier/client names, `gsessionid` and `SID` before the phase closes. Localhost inspection in plan 114-05 already caught this class earlier, when it was still cheap |
| T-114-30 | Denial of Service | The head-blocking vendor script breaking the app for ad-blocked or offline users | mitigate | Task 2 observes the blocked path directly: every view rendering plus a successful real write, with `window.Sentry` undefined |
| T-114-31 | Tampering | Misattributing an ad-blocker block to a CSP failure and then over-widening the policy in response | mitigate | Task 1 requires a clean, unblocked profile, and distinguishes `(blocked:csp)` from `ERR_BLOCKED_BY_CLIENT` in the acceptance criteria; the fallback ladder widens one rung at a time and only in response to a named CSP violation |
| T-114-32 | Tampering | The verifier's own browser left permanently un-instrumented by a forgotten DevTools block rule | mitigate | Explicit final step removing the block rule, with a post-removal `typeof window.Sentry` assertion |
