verification procedures a durable home.

verification (114-05, 114-06) is empirical rather than diff-based.

Purpose: make the ingest request legal, and make the check repeatable.

`## Verifying Sentry / CSP Changes` section.

    **Decide the host form first — this closes the CONTEXT.md discretion item.** Use the **exact**
    host from the DSN, written as `https://o<ORGID>.ingest.<REGION>.sentry.io`. Not
    `https://*.ingest.sentry.io`, not `https://*.sentry.io`. A CSP host-source with no wildcard
    matches exactly one origin, which is the narrowest policy that still permits the SDK's envelope
    POST. A wildcard would additionally authorize outbound POSTs to any other organization's ingest
    endpoint on that domain — a real, if unlikely, data-egress channel in a financial app — and buys
    nothing, since the org id and region are fixed for the lifetime of this Sentry project.

    Record in the SUMMARY that if plan 114-06's production test event fails with a CSP violation
    naming a host different from the one added here, the fallback ladder is
    `https://*.ingest.<REGION>.sentry.io` first, and only then `https://*.ingest.sentry.io` —
    widening one rung at a time and re-running the test event each time, never jumping to the
    broadest form.

    **Make the edit.** In each of the four CSP strings, append a space followed by
    `https://o<ORGID>.ingest.<REGION>.sentry.io` to the end of the existing `connect-src` source
    list — immediately after `https://www.gstatic.com` and immediately before the `;` that
    terminates `connect-src`. Nothing else changes: not `script-src` (the vendor bundle is
    same-origin, already covered by `'self'`), not `default-src`, `style-src`, `font-src`,
    `img-src`, or `frame-ancestors`, and none of the non-CSP headers in either file.

    **Preserve each file's own syntax.** `_headers` uses bare `Content-Security-Policy: value` lines;
    `netlify.toml` uses `Content-Security-Policy = "value"` inside a `[headers.values]` table. The
    surrounding syntax differs; the CSP **value string** must come out byte-identical across both
    files and across both blocks within each file. Netlify's own documentation does not define which
    file wins when both set headers for the same path, so byte-identity is the invariant that makes
    the question moot.

    **One commit, all four occurrences.** Message:
    `fix(114-03): allow Sentry ingest host in connect-src across all four CSP occurrences`. This is a
    deliberate tightening of the Phase 58 Plan 02 precedent, which used two commits.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Netlify edge → browser | The CSP response header is the only mechanism constraining where this app's JavaScript may send data. Widening it is a deliberate reduction of that constraint. |
| Browser → arbitrary `*.sentry.io` origins | Whatever `connect-src` permits, any script on the page (including a future compromised dependency) may POST to |
| Committed config → served config | Two files independently define the same header, and Netlify does not document which wins |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-13 | Information Disclosure | Over-broad `connect-src` widening | mitigate | Add only the exact `https://o<ORGID>.ingest.<REGION>.sentry.io` origin. A wildcard would authorize POSTs to every Sentry tenant's ingest endpoint, turning the CSP relaxation into a general-purpose exfiltration channel for any future injected script. Acceptance criteria assert zero `*` characters in the added source |
| T-114-14 | Tampering | Collateral edit to another directive while hand-editing four long single-line strings | mitigate | `diff` assertion: stripping the added token from each edited file must reproduce the pre-phase (`$BASE`) file byte-for-byte |
| T-114-15 | Repudiation | `_headers` and `netlify.toml` drifting, leaving the served policy unknowable from the repo | mitigate | Byte-identity asserted mechanically (`sort -u | wc -l` over all four occurrences outputs `1`), plus the live read-back procedure written into `HEADERS-README.md` (D-18) and executed in plan 114-05 |
| T-114-16 | Denial of Service | Partially applied CSP blocking ingest on routes nobody tested | mitigate | Single-commit requirement across all four occurrences, asserted via `git show --stat` and `--numstat` |
| T-114-17 | Spoofing | Adding a mistyped host that silently matches nothing | mitigate | The host is copied from the real DSN recorded in `114-01-SUMMARY.md`, and the only proof it is correct is plan 114-06's live production test event — which is precisely why that gate is mandatory rather than optional |
