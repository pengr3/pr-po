    Three sub-steps, one commit.

    **(a) Resolve the version.** Query the live source for the current stable `@sentry/browser`
    release — `curl -s https://api.github.com/repos/getsentry/sentry-javascript/releases/latest`
    and read `tag_name`, cross-checked against
    `curl -s https://registry.npmjs.org/@sentry/browser/latest` and its `version` field. If the two
    disagree (as they did during research), pin the **lower** of the two — the one both sources
    agree exists — and record both observed numbers plus the choice in the SUMMARY. Call the
    resolved value `<VERSION>` below. Do not use `10.70.0` or `10.69.0` unless the live check
    independently produces it today.

    **(b) Download the error-only bundle and commit it.** Fetch
    `https://browser.sentry-cdn.com/<VERSION>/bundle.min.js` and write it to `lib/obs.min.js`
    verbatim — do not reformat, do not strip the library's leading `/*! @sentry/browser ... */`
    banner, do not append anything. The filename is `obs.min.js`, never `sentry.min.js` (D-07: the
    whole point of self-hosting is ad-blocker evasion, and a path containing `sentry` is still a
    filter-list match). The URL must end in exactly `/bundle.min.js` — never
    `bundle.tracing.min.js`, `bundle.tracing.replay.min.js`, or any `.feedback.` variant; those
    physically ship Tracing/Replay/Feedback code and there is no bundler here to tree-shake it away.

    **(c) Establish provenance.** Compute `openssl dgst -sha384 -binary lib/obs.min.js | openssl base64 -A`
    and record it. Cross-check the artifact against an independent origin by fetching
    `https://cdn.jsdelivr.net/npm/@sentry/browser@<VERSION>/build/bundle.min.js` and comparing
    SHA-384 digests. If the digests match, provenance is two-source-confirmed. If the jsDelivr path
    404s or the digests differ, keep the `browser.sentry-cdn.com` copy, record the discrepancy
    explicitly in the SUMMARY as a residual supply-chain risk, and do not silently proceed as if it
    matched.

    **SRI decision — resolve it here, in writing (this closes the CONTEXT.md discretion item):**
    **SRI is NOT applied.** Record this rationale in the SUMMARY: research assumed a third-party CDN
    `<script>` tag, where `integrity` protects against a remote origin serving different bytes at
    runtime. D-07 self-hosts same-origin, so any attacker who can alter `lib/obs.min.js` can equally
    alter the `integrity` attribute in `index.html` — the hash defends nothing and becomes a second
    hand-maintained constant to forget on every version bump, in a repo with no build step to
    recompute it. Provenance is instead established **once, at pin time** by step (c), and the
    SHA-384 digest is recorded in `CLAUDE.md` (plan 114-04) so a future re-download can be
    eyeball-verified against it. Plan 114-04 will assert `index.html` contains zero `integrity=`
    attributes.

    Commit `lib/obs.min.js` alone with message
    `chore(114-01): pin self-hosted Sentry browser SDK <VERSION> as lib/obs.min.js`.
    Do not touch `index.html` in this plan — an uninstantiated vendor file is inert; wiring is
    114-04's job and belongs in its own reviewable diff.

    **The SUMMARY for this plan is a load-bearing artifact**, not a formality — plans 02, 03 and 04
    read it instead of re-asking a human. It must record, as literal values: the full DSN, the org
    id, the region, the derived ingest host `o<ORGID>.ingest.<REGION>.sentry.io`, the resolved
    `<VERSION>`, both version numbers observed in step (a), the SHA-384 digest, the exact download
    URL, the download date, whether the jsDelivr cross-check matched, and the SRI decision.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Sentry CDN (third-party origin) → this repo | A vendor artifact fetched once over the network becomes permanently trusted, same-origin, blocking-parse JavaScript on every page load for every user |
| Sentry SaaS ← this app | The DSN authorizes anonymous event submission into a third-party system from any client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-01 | Tampering | `lib/obs.min.js` download | mitigate | Fetch over HTTPS from `browser.sentry-cdn.com`; cross-check the SHA-384 digest against the independently-served `cdn.jsdelivr.net/npm/@sentry/browser@<VERSION>` copy; record digest + URL + date in the SUMMARY and (114-04) in CLAUDE.md so any future re-download is diffable |
| T-114-02 | Tampering | Wrong bundle variant | mitigate | Assert `grep -c replayIntegration` and `grep -c browserTracingIntegration` are both `0` and raw size < 150000 bytes — a tracing/replay bundle would silently ship code that is explicitly out of scope and opens a PII surface (Replay) this milestone rejected |
| T-114-03 | Spoofing | DSN committed in client code | accept | A Sentry DSN is a public write-only ingest key by design; it grants event submission, never dashboard read. Worst case is third-party event injection consuming free-tier quota — bounded by Sentry's own rate limiting and Spike Protection, and not preventable in a static SPA with no server to proxy through |
| T-114-04 | Elevation of Privilege | Sentry onboarding wizard's Loader Script | mitigate | Explicitly instructed to skip it — the Loader Script self-updates outside version control, which on a no-CI, no-staging, no-rollback-gate app is an uncontrolled remote code change to every user's browser |
| T-114-SC | Tampering | Package-manager installs | n/a | This repo has no npm/pip/cargo install step and no `package.json` dependency graph — the sole supply-chain surface is the single hand-downloaded vendor file covered by T-114-01/T-114-02 |
</threat_model>
