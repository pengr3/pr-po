<objective>
Land every ADDITIVE server-side change this phase needs, so that the client conversions in later waves have somewhere safe to land. Nothing here removes a permission or narrows a query shape.

Two independent problems are solved:

1. **Composite indexes.** Three client queries in later waves pair an existing equality filter with `where('personnel_user_ids','array-contains',uid)`. Firestore requires a composite index for that pairing, index builds take minutes on a live database, and the deploy is a *different* command from the rules deploy. The indexes must exist before the queries ship.

2. **The frozen-array trap.** D-08 stops `assigned_project_codes` / `assigned_service_codes` from ever being written again. Every `firestore.rules` branch that calls `isAssignedToProject()` / `isAssignedToService()` reads those arrays off the actor's own user document. Once they freeze, a user assigned AFTER this phase loses authority those branches grant — a services-side and plan-task-side variant of the exact defect this phase exists to eliminate. RESEARCH.md scoped its audit to READ rules only (`113-RESEARCH.md`, Priority 1 method note: "Write operations are excluded"), so this set of branches was never enumerated. They are enumerated here.

Purpose: make the later client conversions possible without any window in which a scoped role is denied.
Output: `firestore.indexes.json` + `firestore.rules` + `test/firestore.test.js`, all additive, ready for the Wave-2 deploy gate.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser client → Firestore | The only authorization layer is `firestore.rules`. Every client query is attacker-controlled; the rule must be provably sufficient on its own. |
| actor's own `users/{uid}` doc → rule evaluation | `getUserData()` dereferences the actor's own document. Its `all_projects` / `all_services` / `assigned_*_codes` fields are inputs to authorization decisions. |
| child task doc → parent container doc | New in this plan: `project_tasks` / `service_tasks` authorization now dereferences the parent `projects` / `services` document via a denormalized `project_id` / `service_id`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Elevation of Privilege | widened `services` allow list/update branches | mitigate | The new term is `request.auth.uid in resource.data.personnel_user_ids`, evaluated per document against the container the admin already owns. It grants authority ONLY over documents that already name the actor. Task 2 item 7 asserts a non-member role gains nothing. |
| T-113-02 | Elevation of Privilege | `project_tasks` / `service_tasks` parent-`get()` term | mitigate | The `get()` target is derived from the task document's own `project_id` / `service_id`, not from `request.resource.data` on update/delete — so an attacker cannot redirect the lookup at a project they ARE assigned to in order to edit a task belonging to one they are not. On CREATE the id does come from `request.resource.data`, but create authority is exactly "may I create a task under this parent", which is the correct question. |
| T-113-03 | Denial of Service (self-inflicted) | any narrowing rule change | accept-by-design | This plan makes zero narrowings. Every edit is an OR-alternative. The narrowing lives in plan 113-10, behind a production-verification gate. This is the structural mitigation for the phase's headline risk. |
| T-113-04 | Denial of Service (self-inflicted) | missing composite index at query time | mitigate | The 3 indexes ship and are deployed (Wave 2) before any query that needs them (Wave 4). The Wave-2 runbook requires index state `Enabled` before proceeding. |
| T-113-05 | Information Disclosure | hoisted `getUserData().all_services == true` top-level OR | accept | This makes the D-09 escape hatch effective for `operations_user` as well as `services_user`. `all_services` is an explicitly-granted see-all flag (D-09 defines it as a grant, not assignment data); an actor holding it is intended to see everything. Task 2 item 3 pins the behaviour so a future change cannot silently alter it. |
| T-113-06 | Repudiation | extra document reads inside rules | accept | Each widened branch may cost up to 2 extra document accesses (`exists()` + `get()`), well inside Firestore's 10-access limit for single-document requests, and only when the legacy short-circuit misses. Billing impact is negligible at this project's scale. |
| T-113-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs no packages. `113-RESEARCH.md` "Package Legitimacy Audit" records N/A for the whole phase — it is a rules + client-JS change inside the already-vendored Firebase SDK v10.7.1 CDN. |
</threat_model>
