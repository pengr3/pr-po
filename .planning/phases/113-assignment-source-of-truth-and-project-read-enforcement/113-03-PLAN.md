<objective>
Move the single source of truth for "what is this user assigned to" from the frozen `assigned_*_codes` arrays to live `personnel_user_ids` membership — WITHOUT changing the signature or the `null`-means-see-all contract of `getAssignedProjectCodes()` / `getAssignedServiceCodes()`.

This is the linchpin of the phase. There are roughly ten client-side consumers of these two helpers (`projects.js:152,805`, `services.js:144,831`, `project-detail.js:562`, `service-detail.js:773`, `mrf-form.js:1150,1179`, `procurement.js:2898,2981-2982`). Repointing the two helpers fixes all of them at once. In particular it fixes `procurement.js`'s `isMrfInAssignedScope()` (D-04's no-leak invariant), which is expressed in terms of CODE lists and therefore cannot be rewritten in terms of personnel membership at the call site — it needs a code list, and this plan is what keeps that code list truthful once the sync pipelines die.

Nothing is deleted in this plan. The two sync functions in `app/utils.js` stay until plan 113-09, because five other modules still import them.

Purpose: one central repoint instead of ten scattered ones; keeps D-04's invariant logic byte-identical.
Output: a personnel-derived, listener-backed, fail-closed assignment cache wired into the auth bootstrap.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `window._personnelAssignedCodes` → authorization-adjacent UI decisions | This global feeds every client-side visibility filter. It is a CONVENIENCE boundary, not a security boundary — a browser user can overwrite it. Server-side enforcement is `firestore.rules` (plans 113-01 / 113-10). |
| Firestore personnel query → cache contents | Only documents Firestore actually returns can enter the cache, and post-113-10 Firestore only returns documents the actor is a member of. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-11 | Elevation of Privilege | client tampering with `window._personnelAssignedCodes` | accept | This global controls UI filtering only. Every read it influences is independently gated by `firestore.rules`; after plan 113-10 a tampered cache cannot make Firestore return an unassigned project. Documented explicitly so it is never mistaken for a control. |
| T-113-12 | Information Disclosure | cache populated but not cleared on sign-out / user switch | mitigate | Task 2 calls `destroyAssignedCodesListeners()` in both the deactivated path and the signed-out branch, and re-initialises on role change. The teardown resets the cache to `{ projects: [], services: [] }` (fail-closed), not to `null`. |
| T-113-13 | Denial of Service (self-inflicted) | empty cache at first render causes "sees nothing" flash | mitigate | Task 2 awaits the first snapshot of every attached dimension before `handleInitialRoute()`. On failure the catch continues with the fail-closed `[]`, which is a visible-but-safe degradation rather than an unscoped fallback. |
| T-113-14 | Spoofing | a listener error silently leaving stale data | accept | The error callback keeps the last known value and logs with a `[AssignedCodes]` prefix rather than clearing to `null`. Clearing to `null` would mean "see everything" — the dangerous direction. Staleness is the safe failure mode here. |
| T-113-15 | Information Disclosure | personnel listener attached for a see-all role | mitigate | Listeners are attached only for dimensions where the helper would NOT short-circuit to `null`, so a see-all role never issues the scoped query at all and its cache stays empty and unread. |
| T-113-SC | Tampering | npm/pip/cargo installs | n/a | No packages installed. |
</threat_model>
