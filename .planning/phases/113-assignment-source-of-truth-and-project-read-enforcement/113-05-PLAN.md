<objective>
Convert the three project-detail-adjacent read surfaces.

`project-detail.js:220` and `project-plan.js:258` are structural twins: both look a project up by `where('project_code','==',projectCode)`, which is a LIST operation and therefore provably unsatisfiable under an array-contains-only rule. Both must carry the array-contains clause on the same query for scoped roles. Their doc-ID `getDoc` fallbacks need no change at all — a single-document `get()` is evaluated against the actual document's fields, so an array-contains rule condition applies cleanly with no query-shape problem.

`expense-modal.js` issues the SAME `where('project_name','==',identifier)` list query three times per modal open (lines 50, 71, 109). The only scoped-role caller, `project-detail.js:3771`'s `openFullBreakdown`, already holds `currentProject` in memory. Passing it in eliminates all three queries and a pre-existing threefold redundancy at once. The `finance.js` callers are see-all roles and keep the name-based query.

Purpose: close the equality-lookup class of read (Shape C) and the redundant-name-lookup class (Shape D) on the project side.
Output: three files whose project reads are either personnel-paired list queries, direct doc `get()`s, or eliminated entirely.
</objective>

| caller-supplied `budget` / `projectCode` → expense modal | Values now flow in from the caller instead of Firestore. |

|-----------|----------|-----------|-------------|-----------------|

Today both are permitted; after 113-10 neither is, for a scoped `*_user`. |
| T-113-22 | Information Disclosure | caller-supplied `budget` trusted by the expense modal | accept | `budget` is display-only financial context that the caller already read from a document Firestore permitted it to read.
