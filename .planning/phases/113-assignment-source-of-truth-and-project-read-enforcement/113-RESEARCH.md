## Summary

The current `projects` read rule (`firestore.rules:229`) is `allow read: if isActiveUser();` — **completely unscoped for every role**. Nothing has been tightened yet; this phase's job is to design and land that tightening plus every client-side query conversion it requires. The `services` collection is NOT a clean template to copy verbatim: its list rule (`firestore.rules:599-603`) is itself a **hybrid** — `operations_user` (cross-dept) is already scoped via `array-contains personnel_user_ids` on the service document (the D-02 target pattern), but `services_user` (home-dept) is still scoped via the legacy `isAssignedToService()` helper, which reads `assigned_service_codes` off the *user's own document* — exactly the field D-08 says to stop reading. `app/views/services.js:893-901` mirrors this split at the client-query layer. This means "mirror the existing services rule" (D-01) and "standardize on array-contains for every scoped read" (D-02) are in tension with each other as literally written today — D-02 is the *aspirational* end-state, not something `services` has fully reached yet. Planning should treat D-02 as authoritative and note that `services.js`'s own home-department query is *itself* a stale pattern this phase's `personnel_user_ids` mandate logically obsoletes, even though CONTEXT.md's phase boundary text frames the work as `projects`-only.

The exhaustive `projects` collection read audit performed here finds **13 read call sites reachable by a scoped role** that need conversion (CONTEXT.md's preliminary audit found 4 confirmed + 4 unconfirmed = 8; this audit confirms all 8 as MUST-CONVERT and adds 5 more: `app/views/project-plan.js:258`, `app/utils.js:368` inside `generateServiceCode`, and re-classifies `app/views/procurement.js:2932`'s "partially scoped" claim as flatly incorrect — it has zero scoping). One of the net-new finds, `app/utils.js:368`, is the highest-severity gap found in this research: it is reachable by `services_admin` creating **any** new service (via 3 separate call sites of the shared `createEngagement()` helper) and its failure is NOT a silent read-degradation — it throws, is caught, and surfaces as `"Failed to create service"`, **completely blocking service creation for `services_admin`** the moment the rule tightens, unless converted. CONTEXT.md's preliminary audit did not examine this function at all.

**Primary recommendation:** Convert every MUST-CONVERT site to the `services.js:876-903` role-branch pattern (exempt roles keep an unscoped/lightly-scoped query; scoped roles get `where('personnel_user_ids','array-contains',uid)`), add the one net-new composite index this pairing requires wherever it's combined with an existing `where`/`orderBy` clause, and sequence the rollout so **client conversions ship and are verified in production BEFORE the rule tightens** (production rules are currently unfixed; a premature rule deploy would hard-break every scoped `*_user`/`services_admin` read path simultaneously). Treat `services.js`'s own `services_user` home-department query as in-scope collateral cleanup under D-07/D-08, not out of scope, because leaving it unconverted means a newly-assigned `services_user` becomes invisible to themselves the moment the sync pipelines that currently keep `assigned_service_codes` alive are deleted.

## Firestore Rules Mechanics (Priority 2)

### Current rule text (as of this research, working tree clean on `firestore.rules` except the uncommitted diff described below)

**`projects` — read (`firestore.rules:227-229`):**
```
match /projects/{projectId} {
  // All active users can read
  allow read: if isActiveUser();
```
This single `allow read` governs BOTH `get()` (single document) and `list()`/collection queries. It is completely unscoped — the target state this phase must replace.

**`services` — get/list split (`firestore.rules:582-603`), the model D-01 says to mirror:**
```
match /services/{serviceId} {
  allow get: if hasRole(['super_admin', 'operations_admin', 'services_admin', 'services_user', 'finance', 'procurement']);

  allow list: if isActiveUser() && (
    hasRole(['super_admin', 'operations_admin', 'services_admin', 'finance', 'procurement']) ||
    (isRole('services_user') && isAssignedToService(resource.data.service_code)) ||
    (isRole('operations_user') && request.auth.uid in resource.data.personnel_user_ids)
  );
```
Key mechanical fact this phase needs to know and CONTEXT.md doesn't state: **`services` already splits `get` from `list` into two separate rules with different permission sets.** `allow get` is broader (includes `services_user` unconditionally, no assignment check) because a single-document fetch by ID is low-risk (you must already know the ID) and cheap to evaluate. `allow list` is the narrow one, because list queries can be used to *discover* documents. This get/list split is a design option this phase should explicitly adopt or reject for `projects` (currently `projects` has ONE unified `allow read` covering both) — several of the MUST-CONVERT sites above (`project-detail.js:225`'s `getDoc` fallback, a `getDoc(doc(db,'projects',mrfData.project_id))` conversion recommended for site #11) would benefit from a permissive `get` / narrow `list` split exactly like `services`.

### Query-vs-rule evaluation semantics (verified against official Firebase documentation — HIGH confidence)

- **Single-document `get()`:** Firestore evaluates the rule against the ACTUAL document's field values (`resource.data` is populated). A condition like `request.auth.uid in resource.data.personnel_user_ids` is evaluated directly, per document, with no constraint on how the client looked the document up. This is why `project-detail.js:225`'s `getDoc()` fallback and a `project_id`-based `getDoc()` conversion both work cleanly under an array-contains condition with zero client-query changes needed beyond knowing the doc ID.
- **Collection/list queries:** "Security rules are not filters — queries are all or nothing." [CITED: firebase.google.com/docs/firestore/security/rules-query] Firestore evaluates the rule against the query's *potential result set*, not the documents actually returned. If the query's `where`/`orderBy` clauses cannot PROVE that every possible matching document would satisfy the rule, the **entire query is rejected** with `permission-denied` — even if, in practice, every document currently in the collection would have passed. This is the exact mechanism behind D-03's "denied in its entirety" framing, now confirmed against official docs rather than asserted from training knowledge.
- **Practical consequence for `where('project_name','==',X)`-shaped queries (sites #7-9, #10, #11):** these can NEVER satisfy an `array-contains personnel_user_ids` rule on their own, because the rule requires the query to also carry a `where('personnel_user_ids','array-contains',uid)` clause — an unrelated equality filter provides no such proof. The two fixes are: (a) add the array-contains clause to the SAME query (requires a new composite index, see below), or (b) route the lookup through a `get()` instead of a `list()`.

### Composite index implications [CITED: firebase.google.com/docs/firestore/query-data/index-overview, cross-referenced with community sources]

- `firestore.indexes.json` currently declares 18 composite indexes; **zero reference `personnel_user_ids`** (confirmed via full-file grep). The only existing `array-contains`-style scoped query in the codebase (`services.js:893`, `where('personnel_user_ids','array-contains',uid)` with no other `where` clause) needed no composite index because it's single-field — Firestore auto-indexes single fields.
- The moment this phase pairs `array-contains` with an EXISTING equality filter (e.g., site #2's `where('active','==',true)` + a new `where('personnel_user_ids','array-contains',uid)`, or site #3/#4's `where('project_code','==',X)` + array-contains), Firestore will almost certainly require a NEW composite index that does not exist today. Firestore surfaces this as a runtime error containing a direct console link to auto-create the index — but that is a manual, human-in-the-loop step (`firebase deploy --only firestore:indexes`, or click the console link), separate from `firebase deploy --only firestore:rules`. **This is a genuine deploy-time surprise**: a plan that only accounts for a rules deploy will discover missing-index errors live, mid-testing, for every paired query. Recommend the plan explicitly enumerate every new composite index needed (derivable from the audit table above) and add them to `firestore.indexes.json` BEFORE the corresponding client query ships, with a `firebase deploy --only firestore:indexes` step called out as its own checkpoint (indexes can take minutes to build on a live database, unlike rules which apply instantly).
- Sites that avoid this entirely by using a bare array-contains query with NO other `where` clause (site #1, #5, #6 if the `active`/unfiltered constraint is dropped and re-applied client-side post-fetch) need no new index — this is the cheapest, lowest-risk conversion shape and should be preferred wherever the extra client-side filter is affordable (small assignment-scoped result sets).

### Deploy ordering (Risk — Priority 5, mechanically grounded here)

Because `list()` denial is total (not partial), the **only safe rollout order** is: (1) ship every MUST-CONVERT client query change (still running against the CURRENT unscoped rule, so nothing breaks — these are strict narrowings that produce correct results even before the rule tightens, since the unscoped rule admits any query shape); (2) verify in production that scoped roles still see correct data with the new, narrower queries; (3) ONLY THEN tighten `firestore.rules`'s `projects` (and, if in scope, `services`) read rule and deploy it. Deploying the rule change first — or in the same push as an incomplete client conversion — would immediately and totally break every scoped role's `projects` access, matching exactly the class of defect this phase exists to fix. CONTEXT.md's `<specifics>` section confirms production rules are currently unfixed for the *prior* (services-user-project-hidden) defect too — there is already one rules-deploy debt riding into this phase; this phase adds its own, larger one.
