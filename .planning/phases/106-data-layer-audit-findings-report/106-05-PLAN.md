    Two sweeps:
    1. N+1 — find loops that issue a per-iteration read. `grep -rnE "for \(|\.forEach\(|\.map\(" app --include=*.js`, then for candidates check whether a `getDoc(` / `getDocs(` sits INSIDE the loop body (a per-row fetch over another collection). Each such fan-out is an N+1: write an E-0N finding naming the outer collection, the per-row read, and the anchor. Recommend batching (in-query / a single getDocs + in-memory join, or `where(documentId(),'in',[...])`). Severity: Medium.
    2. CLIENT-SIDE FILTERING — `grep -rnE "getDocs\(" app --include=*.js` then inspect whether the result is immediately narrowed with `.filter(...)` / `.find(...)` / a manual loop that a Firestore `where(...)` could have done server-side. Each is an E-0N finding: fetches the whole collection then discards rows client-side. Cross-ref the where(183)-vs-limit(12) imbalance — many listeners over growing collections (mrfs, prs, pos, notifications, activity_entries, edit_history) have no limit(). Recommend where()/limit(). Severity: Medium (client-side filter / missing limit on a growing collection); Low if the collection is bounded/small.

Copy each getDocs anchor verbatim from the inventory and classify it — most are a quick verdict from the inventory's trimmed line; deep-read only the suspicious ones. This proves every read site was examined for N+1 / client-side filtering, not only the flagged ones.
