## OMITTED KPI Chips (source could not be confirmed as a queryable field)

| Chip | Role | Reason |
|------|------|--------|
| **Collectibles Due** | finance | Collectible payment status is DERIVED from `payment_records` arithmetic at render time (never stored — finance.js `deriveCollectibleStatus`, D-19). No queryable "due" field; a raw `collectibles` count would include fully-paid rows and be misleading. Per omit rule → skipped. |
| **Payables Owed** | finance | There is NO `payables` collection. Payables are derived from `pos` + `rfps` remaining-balance arithmetic (`derivePOSummary`). Replicating that in the KPI module = "copy logic" the plan forbids. Per omit rule → skipped. |

Net effect: finance sees **1 chip** (PRs/TRs to Approve). The plan's Task 1 acceptance explicitly allows "finance sees Collectibles/Payables/PR-TR (or fewer if a finance collection can't resolve)".

## Deviations from Plan

### 1. [Rule 3 — clean intermediate commits] `delete window.ccScrollTo` added in Task 1, not Task 3
- **Found during:** Task 1
- **Issue:** The plan assigns "delete window.ccScrollTo in destroy()" to Task 3, but Task 1 registers `window.ccScrollTo`. Leaving it registered-without-cleanup across the Task 1→2 intermediate commits is a latent leak (destroy() would orphan the handler).
- **Fix:** Registered AND deleted `window.ccScrollTo` in Task 1 (same commit). Task 3 adds `delete window.ccOpenActivity`. Final state is identical to the plan; every intermediate commit is leak-free. Mirrors 107.3's own "keep intermediate commits valid" re-sequencing.
- **Committed in:** `f003f166` (Task 1)

### 2. [Rule 2 — correctness / omit rule] Finance money chips omitted (documented above)
- **Found during:** Task 1 (finance.js source confirmation)
- **Issue:** Neither "Collectibles Due" nor "Payables Owed" maps to a confirmable queryable field.
- **Fix:** Omitted both chips rather than render a wrong/0 value. Documented in the OMITTED table.
- **Committed in:** `f003f166` (Task 1)

### 3. [Rule 3 — shared infra] `loadYourWorkData()` cache introduced in Task 1
- **Found during:** Task 1
- **Issue:** The *_user KPI chip "My Open Items = Your-Work total" needs the same data Task 2's Your Work panel renders. Fetching twice would be wasteful.
- **Fix:** Introduced a shared `loadYourWorkData(user)` helper + `_ccYourWork` module cache in Task 1 (the KPI chips need it); Task 2's `renderYourWork` reuses the cache. One fetch per view-load. Cache invalidated (`_ccYourWork = null`) at each init + Refresh + in destroy().
- **Committed in:** `f003f166` (Task 1) / reused in `b6daa584` (Task 2)

No architectural changes (Rule 4). No auth gates encountered.
